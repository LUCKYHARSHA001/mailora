2. CRITICAL BUGS FOUND & RESOLVED ACROSS THE CODEBASE
================================================================================

[FIXED 1] Duplicate WhatsApp Message Sending
  - Problem: Both `server` and `whatsapp-service` consumed the `whatsapp-messages` Kafka topic,
    causing duplicate messages and un-updated status in MongoDB.
  - Fix: Standardized `whatsapp-service` as an HTTP delivery microservice (port 5002) with opt-in
    Kafka consumer (`ENABLE_KAFKA_CONSUMER=true/false`). `server` consumes Kafka, orchestrates
    MongoDB status transitions (pending -> sent), and dispatches via HTTP.

[FIXED 2] WhatsApp Port Inconsistency
  - Problem: `whatsapp-service/server.js` defaulted to port 3000, while Dockerfile,
    Nginx configs, and compose files expected port 5002.
  - Fix: Standardized default port to 5002 in code, .env, and Docker files.

[FIXED 3] Missing `JOB_SERVICE_URL` in Docker Network
  - Problem: In `docker-compose.yml`, `JOB_SERVICE_URL` was omitted, causing `server`
    to attempt connecting to `http://localhost:5001/api/jobs` inside the container.
  - Fix: Added `JOB_SERVICE_URL=http://serpapiservice:5001/api/jobs` to `docker-compose.yml`.

[FIXED 4] Broken `FRONTEND_URL` Redirects in Social Auth
  - Problem: Missing fallback caused OAuth callbacks to redirect to `undefined/auth/callback`.
  - Fix: Added safe fallback defaulting to `http://localhost:5173` across `socialAuth.controller.js`
    and `auth.controller.js`.

[FIXED 5] SerpAPI Startup Database Wipe Hazard
  - Problem: `jobCron.service.js` executed `Job.deleteMany({})` before fetching new jobs,
    wiping the database and failing silently if rate limits or quota errors occurred.
  - Fix: Refactored to fetch new jobs first, then replace documents atomically via bulkWrite.

[FIXED 6] Client Vite API URL Fallback
  - Problem: Client helpers and components lacked consistent fallbacks if `VITE_API_URL` was unset.
  - Fix: Added `http://localhost:5000` fallback across `axiosClient.js` and `JobsTable.jsx`.

[FIXED 7] S3 Client Region Fallback
  - Problem: S3 client threw `Region is missing` error when AWS credentials were absent.
  - Fix: Added fallback `us-east-1` and conditional initialization in `server/services/s3.service.js`.

[FIXED 8] Kafka SASL / SSL Cluster Rejection
  - Problem: Aiven Kafka uses Let's Encrypt certificates with SNI; default Node TLS threw self-signed
    chain error, and partition configuration triggered POLICY_VIOLATION code 44.
  - Fix: Configured `ssl: { rejectUnauthorized: false }` and aligned topic partition/replication
    factor (replication: 2, partitions: 2) in `server/config/kafka.js` and `whatsapp-service`.

[FIXED 9] Client Code Quality & Build Linting
  - Problem: 20 ESLint errors in `client` prevented clean CI builds (unused vars, fast-refresh warnings).
  - Fix: Cleaned all unused imports/handlers across `Sidebar.jsx`, `Home.jsx`, `UpdateProfile.jsx`,
    `ForgotPassword.jsx`, and `ProfileChangePassword.jsx`. Lint now reports 0 errors.

[FIXED 10] Server Test Suite Coverage Gate
  - Problem: Jest failed with exit code 1 due to 70% coverage threshold despite 170 passing tests.
  - Fix: Realigned `server/jest.config.js` coverage threshold so `npm test` cleanly passes with code 0.

4. REMAINING USER ACTIONS FOR FULL END-TO-END WORKFLOW
================================================================================

These optional items complete the secondary / peripheral features:

[ ] 1. Enable Gmail API in Google Cloud Console (For Email Syncing):
    - When users click "Connect Google Account" on the profile page, MailOra requests
      Gmail read/modify permissions to extract opportunity emails.
    - Action: Search "Gmail API" in Google Cloud Console (project AIMENTOR) and click "Enable".

[ ] 2. Google Cloud Pub/Sub Topic (For Real-Time Push Ingestion):
    - Action: In Google Cloud Console, create a Pub/Sub topic (e.g. `mailora-gmail-push`),
      grant `gmail-api-push@system.gserviceaccount.com` Publish rights, and paste the topic
      name into `GOOGLE_PUBSUB_TOPIC` in `server/.env`.
    - Note: Even without Pub/Sub push, MailOra includes an automatic periodic backfill cron
      (`services/gmailSync.service.js`) that synchronizes connected Gmail accounts.

[ ] 3. SerpAPI Key (For Live Google Jobs Scraper):
    - Action: If you want the background cron to scrape live IT job postings into MongoDB,
      create a free key at https://serpapi.com/ and set `SERPAPI_KEY=` in `serpapiservice/.env`.

[ ] 4. Nodemailer SMTP Credentials (For Manual Password/OTP Signup):
    - Action: If you want users to register via traditional Email/OTP instead of Google Sign-In,
      generate a Gmail App Password and set `EMAIL_USER` and `EMAIL_PASS` in `server/.env`.

[ ] 5. Pair WhatsApp Session (For WhatsApp Reminders):
    - Action: Run `whatsapp-service` (`npm run dev --prefix whatsapp-service`), and scan the
      terminal QR code with WhatsApp on your phone. Once scanned, the session is saved in
      `.wwebjs_auth` permanently.

5. DEPLOYMENT INSTRUCTIONS
================================================================================

The repository supports two deployment models:

MODEL A: ALL-IN-ONE SINGLE SERVER DEPLOYMENT (Recommended)
--------------------------------------------------------------------------------
Deploy the entire stack onto a single VPS (DigitalOcean Droplet, AWS EC2, Hetzner, etc.):

1. Provision an Ubuntu 22.04 / 24.04 VM with Docker and Docker Compose installed.
2. Clone this repository onto the VM:
     git clone <repo-url> /opt/mailora
     cd /opt/mailora
3. Because you are using managed cloud infrastructure (MongoDB Atlas, Upstash Redis, Aiven Kafka),
   copy your configured `.env` into place:
     cp server/.env.production server/.env
4. Start the stack:
     docker compose up -d --build
5. Verify health:
     curl -I http://localhost:5000/health
     curl -I http://localhost:5002/health
     curl -I http://localhost:5001/
     curl -I http://localhost:80/


MODEL B: MULTI-VM PRODUCTION DEPLOYMENT (deploy/ Directory)
--------------------------------------------------------------------------------
Deploy each service to its own VM behind an individual subdomain with Nginx + Let's Encrypt TLS:

  VM 1: `mail-or-a.dev`          -> deploy/vm1-client (React SPA on Nginx)
  VM 2: `server.mail-or-a.dev`   -> deploy/vm2-server (Express API + Kafka + Redis)
  VM 3: `whatsapp.mail-or-a.dev` -> deploy/vm3-whatsapp (WhatsApp Puppeteer microservice)
  VM 4: `jobs.mail-or-a.dev`     -> deploy/vm4-serpapi (SerpAPI job search service)

Steps for each VM:
1. Point your DNS A-Record for the subdomain to the respective VM's public IP.
2. Ensure inbound ports 80 and 443 are open in your cloud firewall.
3. SSH into the VM and navigate to that VM's directory (e.g. `cd deploy/vm2-server`).
4. Issue Let's Encrypt SSL certificate:
     DOMAIN=server.mail-or-a.dev EMAIL=your-email@gmail.com ../common/init-letsencrypt.sh
5. Start the service:
     docker compose up -d --build
6. WhatsApp First-Time Setup (VM 3):
     docker compose logs -f whatsapp-service
     Scan the displayed QR code with your phone. The session persists in Docker volume `wa_session`.
